- `npm run dev` — Vite dev server (TanStack Start, SSR)
- `npm run build` / `npm run preview`
- `npm run lint` — ESLint; `npm run format` — Prettier
- `npm test` — Vitest once (jsdom, setup in `src/test/setup.ts`, matches `src/**/*.{test,spec}.{ts,tsx}`)

## Stack

TanStack Start (React 19, file-based routing, server functions) + TanStack Query, Tailwind v4, shadcn/ui (`src/components/ui`, config in `components.json`), Supabase (Lovable Cloud) for auth and Postgres. Deploy target is Cloudflare via nitro.

`vite.config.ts` uses `@lovable.dev/vite-tanstack-config`, which already bundles tanstackStart, React, Tailwind, tsconfig paths, the `@` alias, nitro, and env injection — do not add those plugins again. `vitest.config.ts` is separate and defines its own `@` alias.

## Architecture

**App purpose:** "Growth Health Check" — a 10-question yes/no business assessment. Each "no" lowers the score and surfaces a weakness (title + description stored per question in the DB) on the report.

**Routing** (`src/routes/`, see `src/routes/README.md` for TanStack conventions — no Next.js-style `pages/` or `app/`):
- Public: `/` (landing), `/auth`, `/reset-password`
- `_authenticated/route.tsx` is a pathless layout with `ssr: false` that checks `supabase.auth.getUser()` in `beforeLoad` and redirects to `/auth`. Protected pages (`assessment`, `reports`, `report.$id`) live beneath it.

**Server functions and auth flow:**
- `src/start.ts` registers `attachSupabaseAuth` as global function middleware — it attaches the browser session's bearer token to every server-fn RPC. It also registers the error-page and CSRF request middleware (defining `start.ts` opts out of the default CSRF middleware, so it must remain explicit).
- Server functions (`src/lib/*.functions.ts`) use `.middleware([requireSupabaseAuth])`, which validates the JWT and provides `context.supabase` (a user-scoped client, so RLS applies) and `context.userId`.
- `src/integrations/supabase/client.server.ts` exposes `supabaseAdmin` (service role, bypasses RLS). Route files and `*.functions.ts` are shipped to the client bundle, so only import it dynamically inside handlers (`await import(...)`) or from other `.server.ts` modules.

**Assessment domain:**
- `src/lib/assessment.ts` — pure, shared logic: the `QUESTIONS` list, the `answersSchema` zod validator (exactly 10 unique answers), `scoreAnswers`, and `buildWeaknesses`. Unit tests in `src/test/assessment.test.ts` cover it.
- `src/lib/assessment.functions.ts` — `submitAssessment`, `getReport`, `listMyReports`. Writes go through the `submit_assessment(jsonb)` Postgres RPC; scoring is recomputed on the server rather than trusted from the client.

**Database:** schema and RLS policies live in raw SQL migrations at `drizzle/migrations/` (tables `profiles`, `questions`, `assessments`, `assessment_answers`, plus the `submit_assessment` security-definer function). Users can only read their own rows, and inserts happen solely through the RPC. Generated TS types are in `src/integrations/supabase/types.ts`. `drizzle.config.ts` reads `LOVABLE_DB_MIGRATION_URL`.

**AI action plan (Gemini, optional extension):** additive only. Scores and weaknesses never come from the AI and must not change because of it.
- `src/lib/ai/insights.ts`: pure prompt building, Gemini response schema, and `validatePlan`. The plan must cover exactly the report's weaknesses; anything else is rejected. Bump `PROMPT_VERSION` when the prompt or output shape changes.
- `src/lib/ai/generate-plan.ts`: orchestration with injected deps (rate limit `DAILY_LIMIT`, one retry on off-spec output). Tested in `src/test/ai.test.ts` with no network.
- `src/lib/ai/gemini.server.ts`: REST client (`GEMINI_API_KEY`, optional `GEMINI_MODEL`, default `gemini-flash-lite-latest`; Gemini HTTP 429 maps to a "busy" result). Load it only via `await import()` inside handlers.
- `src/lib/insights.functions.ts`: `getActionPlan` / `generateActionPlan`. Plans are written only with the service role into `assessment_insights` (migration `0001`); users have SELECT only. Until Lovable regenerates `types.ts`, these tables are queried through an `untyped` client cast.
- UI: `src/components/report/ActionPlanSection.tsx`, hidden entirely when no key is configured. Generated on demand only.
- Language: `useAppLanguage()` (`src/hooks/use-app-language.ts`) feeds the plan language; switch it to i18next's resolved language when i18n lands.
- Secrets: put `GEMINI_API_KEY` in `.env.local` locally (gitignored via `*.local`) and in Lovable Cloud secrets for deploys. Never in `.env`, which is committed.

**Error handling:** `src/server.ts` wraps the SSR entry to turn swallowed h3 500s into a rendered error page (`src/lib/error-page.ts`), and `src/lib/error-capture.ts` / `lovable-error-reporting.ts` report errors to Lovable.
